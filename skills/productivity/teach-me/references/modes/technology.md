# Technology lesson

Use for a programming language, library, framework, platform API, or tool.

## Ground truth

Resolve the version before teaching. Use a user-pinned version; otherwise use latest stable unless multiple mainstream tracks materially differ, in which case ask. Record exact package/compiler/runtime versions and official documentation revisions.

Create a disposable verification project or environment and install the actual technology. Run the code, type checks, compiler, or official minimal example that supports the lesson. Use Docker when local installation is missing or disruptive. If verification requires paid access, login, unavailable hardware, or a physical environment, use primary sources and record the boundary instead of involving the learner.

## Lesson shape

Choose one mechanism, not a feature tour. Start with a checkable prediction, then use an authored debugger trace or progressive system view. For code, show the active line and before or after phase; separate source, values, literal output, and conceptual flow.

Cover three to five meaningful cases when behavior branches:

1. normal input;
2. many records or high volume;
3. empty/no input;
4. one important edge or failure case;
5. another case only when common enough to change practice.

End with a transfer task using a different API shape or input. Cite official docs next to claims and keep the verified example frozen in the route.
